# Hosted copperflow, round 1: sign up, connect an agent, watch it draw

Asked by the maintainer (2026-11-11/12): publish copperflow on the maintainer's own server (`copperflow.kurpeeren.com`), outside GitHub, so that people sign up, connect their AI over MCP and use it: the person says "create a new circuit", the agent connects by itself, learns the program at once, attaches the datasheets and draws, while the person watches the same design in the browser.

Nothing in this plan is deployed until the maintainer says so. The plan ends with what only the maintainer can decide.

## Facts (checked in the code on 2026-11-12, main af17861)

- **One user, one folder, one machine.** `copperflow studio --root <folder>` listens on 127.0.0.1 only, refuses any other `Host` or `Origin`, and protects `/api/` with one random session token passed in the URL fragment and sent as `x-copperflow-token` (`src/studio/server.ts`). There are no accounts and no notion of a project owner.
- **The agent connects over stdio.** `copperflow mcp --root <folder>` uses `StdioServerTransport` (`src/cli-commands.ts`): the agent must run on the same machine as the files.
- **A circuit file is code that runs.** `src/engine/evaluate.ts` transpiles `*.circuit.tsx` with esbuild and runs it in a `node:vm` context. Its own comment says it: "A guard against mistakes, not a security boundary … deliberately hostile code can still escape this context. There is no time limit here either; the caller enforces one." Builds, the router and the placer run in `worker_threads` with a heap limit.
- **Live view exists.** The Studio pushes build, route and place events over server-sent events; a second browser on the same project sees the agent's edits as they land.
- **The agent teaches itself in one call.** The server's instructions say to call `project_status` first and follow the skill; the proof of AI co-design round 2 (a cheap model, an empty project, only the skill and the tools) reached a routed, checked, exported board in 21 tool calls and 25 034 characters of answers, 16 161 of them the instructions and the tool list.
- **Pin tables from memory are wrong.** In that proof's second run the model wrote the MCP2515's pins from memory and got them wrong; the board would not have worked. Parts must come from a datasheet the agent has actually read.
- **The LCSC importer's terms.** `docs/licences.md`: the import is offered for personal, non-commercial use on the person's explicit request, on their own machine. A public service changes that reading.

## Global constraints

The repository's constraints hold (English; one-line commits without trailers; small tested modules; typecheck, test and build pass; files as LF; nothing a person placed or locked is moved). The local program keeps working exactly as today: hosted mode is a way of running the same Studio and MCP servers, never a fork of them. No user's code runs in the same process, user or container as another user's data. Secrets live in the server's environment, never in the repository. No new runtime dependency in the local program; the hub may use what Node 22 has built in (`node:sqlite`, `node:crypto`'s scrypt) before reaching for a package, and every package it adds is named in `docs/licences.md`.

## Decisions

- **A hub in front, the unchanged program behind.** A small service, the hub (`src/hub/`), owns accounts, sessions, the list of projects and the public HTTPS endpoint. Behind it, each active workspace is one isolated process tree that runs today's Studio server and today's MCP server against that user's project folder. The hub authenticates every request, finds the workspace, and proxies to it (HTTP, server-sent events, and the MCP stream). The engine, the core, the tools and the Studio's code do not learn about users.
- **Isolation is the operating system's, not the VM's.** A workspace runs in a container: its own user, no network egress, a read-only image, the project folder as its only writable mount, limits on memory, CPU, processes and open files, and a wall-clock limit on every build, route and place run. A workspace starts on the first request and stops after 15 idle minutes. The `node:vm` context stays as the guard against mistakes it is. Running circuit code in an in-process sandbox library was considered and rejected: it adds a dependency, and a single escape would reach every user's files.
- **Workspaces on their own origins.** Each project is served on `<project id>.<workspace domain>`, never on the public origin: content a project serves, or a Studio flaw triggered by project data, must not share an origin with the hub's pages, or it could read the account page and drive its forms. The public origin's `/p/<id>/` hands a signed-in owner over with a one-time token; the project origin has its own cookie, bound to the hub session that made it. Until the container runner exists, the hub starts only with `--trusted-accounts-only`, because the process runner is not a boundary.
- **Accounts for a closed beta.** Sign-up needs an invite code (the maintainer makes them with a CLI command), an email address and a password; passwords are stored as scrypt hashes; sessions are HTTP-only, SameSite cookies. No email is sent in round 1, so no SMTP is needed: a forgotten password is reset by the maintainer's CLI. Open sign-up, email links and third-party login are later rounds.
- **The agent connects by URL.** The hub serves MCP over Streamable HTTP at `https://copperflow.kurpeeren.com/mcp`. Authorisation follows the MCP specification's OAuth 2.1 flow (authorisation code with PKCE, dynamic client registration), so a person adds one URL in their client, signs in in the browser, and approves; for clients without OAuth the account page issues personal access tokens (shown once, stored hashed, revocable). A token names a user, never a folder: the hub maps it to that user's workspaces.
- **Projects, not folders.** Hosted tools gain three calls the local server does not need: `list_projects`, `new_project { name }`, `open_project { name | id }`; every other tool then works on the open project exactly as today. "Create a new circuit" is `new_project` then `new_circuit`. As built (Task 2b): the hub itself is the MCP server the agent talks to; it answers these three and `guide`, and forwards every other tool to the open project's workspace as an MCP client with a ticket signed per request. At the hub, instructions + `tools/list` are 42 725 characters (held at 43 000) and `guide` 15 390. OAuth redirect URIs must be https, or http on loopback, so clients that register a custom-scheme redirect are refused until that is decided.
- **Learning in one call, measured.** The hosted server's instructions stay as short as today's. A `guide { topic? }` tool returns the skill (`SKILL.md`, or one reference by name), because many clients do not read MCP resources by themselves; the skill files are also offered as resources. What connecting costs is measured as a client pays it, in three numbers (test/mcp-hosted.test.ts): the instructions, the full `tools/list` answer as JSON, and the first `guide` answer. Limits: instructions + `tools/list` at most 38 000 characters, `guide` at most 16 000. Measured 2026-11-12 on the hosted server: instructions 907, `tools/list` 40 988 (41 895 together, over the 38 000 target; the test holds it at 42 000), `guide` 15 390. The list already leaves out the JSON Schema plumbing zod adds (patterns, length limits, `$schema`, unbounded integer limits; the tools still check every argument) and the importer; what else could go is in task-1-report.md.
- **Datasheets are part of the part.** `attach_datasheet { part, url, title?, pages? }` records where a part's pin table came from; `create_part` in hosted mode refuses a chip without a datasheet reference unless the description says the pins are not from a datasheet. The person can drop a PDF on a part in the Studio; it is stored in the part's folder inside their own project, never shared between users and never fetched by the server from a URL the agent gives (that would let a caller make the server request any address). The agent reads the PDF with its own client and passes the pin table and the page it came from; `verification.md` cites the file and the page, so the person checks the part against the source in one click. Reading PDFs on the server is a later round.
- **The person watches.** `https://copperflow.kurpeeren.com/p/<project>` is the Studio for that project, behind the session cookie; the fragment token is not used in hosted mode. The agent's changes appear live, as locally; locks, marks and undo work as locally, so the person steers by locking and marking while the agent works.
- **The importer is off in hosted mode** until the maintainer has the source's permission or decides otherwise; the tool answers with the reason and points to `create_part` with a datasheet.
- **Storage and limits.** A user's projects are plain folders under one data directory (`<data>/<user id>/<project>/`), exactly the files the local program writes, so a project downloads as a zip and opens locally, and a local project uploads as a zip. Per user in the beta: 20 projects, 200 MB, 300 parts per circuit, 20 s per route or place run, 60 tool calls per minute. A nightly archive of the data directory goes to a second location the maintainer names.
- **Out of scope in round 1:** teams and sharing a project with another account, two people editing at once, payment, open sign-up, email, reading PDFs on the server, the importer.

## Task 1: the Studio and MCP servers in hosted mode

- `startStudio` takes `{ hosted: { bind, publicOrigin, basePath, workspaceId, ticketPublicKey } }`: binds where it is told, accepts the public `Host` and `Origin`, replaces the fragment token with the hub's signed workspace ticket (a short-lived value the hub adds to each proxied request), and serves under a base path. The local behaviour and its tests are untouched.
- `copperflow mcp --http <port>`: the same server over the SDK's Streamable HTTP transport, bound to the workspace's private interface, trusting only the hub's ticket.
- `guide`, `attach_datasheet`, and the datasheet rule in `create_part` (active when a `hosted` flag is set; the local program gets `attach_datasheet` too, without the refusal).
- Tests: the hosted Host/Origin/ticket rules (a request without a ticket, with another workspace's ticket, with an expired one); the base path; the MCP tools over HTTP give the same answers as over stdio on the demo project; `guide` sizes; the datasheet rule.

## Task 2: the hub

- `src/hub/`: accounts (invite codes, scrypt, sessions), projects (create, list, rename, delete with a typed confirmation, download and upload as zip with the same path checks `resolveInRoot` gives), personal access tokens, the OAuth 2.1 authorisation server for MCP (PKCE, dynamic client registration, consent page), rate limits and quotas, an audit log of sign-ins and token use; state in `node:sqlite`.
- The proxy: HTTP and server-sent events to the workspace's Studio; the MCP stream to the workspace's MCP server; `list_projects`, `new_project`, `open_project` answered by the hub itself.
- Pages: sign up, sign in, projects, account (tokens, connected clients, delete my account and data), a privacy page and a terms page whose texts the maintainer supplies.
- Tests: every route refuses without a session or with another user's project; cross-site request forgery on every state-changing route; token hashing and revocation; the OAuth flow end to end with a test client; quotas; zip upload refusing paths outside the project, links and oversized archives.

## Task 3: the workspace runner

- `src/hub/runner/`: starts a workspace container on demand, stops it when idle, restarts a crashed one once, and reports its state; the container image is built from the repository (`Dockerfile`), runs as a non-root user with no network egress, a read-only root, the project mount, and limits (512 MB, one CPU, 128 processes). A process-per-workspace runner with the same interface exists for tests and for a server without containers, and says plainly that it is not a security boundary.
- Tests (run where containers are available, skipped with a clear message elsewhere): a circuit file that reads a file outside its project, opens a network connection, loops forever, allocates without bound, or spawns processes is contained and reported as a build error; one workspace cannot see another's folder; idle stop and start on demand.

## Task 4: operations

- `deploy/`: a Compose file (hub, the image for workspaces), the reverse-proxy snippet for TLS and server-sent events, the environment file's template, the backup script and its restore test, a runbook (first start, making invite codes, resetting a password, reading the audit log, stopping a workspace, upgrading, rolling back).
- A health endpoint and a status line for the maintainer (`copperflow hub status`: users, active workspaces, disk used).

## Task 5: security review

An independent review of Tasks 1–3 before anything is exposed: authentication and session handling, authorisation on every route and every proxied path, request forgery, the OAuth flow, path handling in uploads and project names, the datasheet store, the container's limits, what the audit log records, and what an error message reveals. Every Critical and High finding is fixed and re-reviewed before Task 6.

## Task 6: proof (controller, then the maintainer)

1. On the maintainer's machine first, with the hub and the runner started locally: a second account cannot list, open, read or change the first account's project through the pages, the proxy or MCP; the hostile circuit files of Task 3 are contained.
2. A fresh agent on a cheap model is given only the server's URL and a token: it connects, calls `guide`, creates a project and the CAN module from the brief of the round 2 proof with the two datasheets attached, and reaches a routed, checked, exported board. Measured as before: tool calls and characters of answers.
3. Only after the maintainer's go-ahead: the closed beta on `copperflow.kurpeeren.com` with invite codes; the maintainer adds the URL in their own client, says "create a new CAN module", and watches it draw in the browser.

## For the maintainer to decide (nothing here is assumed)

1. **The server**: Docker is available on it (the maintainer, 2026-11-12), so workspaces run in containers as decided above. Still open: its operating system, which reverse proxy already serves `kurpeeren.com`, and how much memory and disk the beta may use.
2. **Who may sign up**: invite codes only (this plan), or open sign-up later, which needs email, abuse handling and a way to answer people.
3. **The texts**: the privacy and terms pages. The service stores an email address, a password hash, the projects and an audit log; if people in Turkey or the EU use it, the personal-data rules (KVKK, GDPR) apply to the maintainer as the operator.
4. **The LCSC importer**: stays off in hosted mode, or the maintainer asks JLCEDA/EasyEDA for permission.
5. **Backups**: where the nightly archive goes.
6. **The domain**: the DNS record for `copperflow.kurpeeren.com`, made by the maintainer when Task 6 step 3 is reached, and a wildcard DNS record for the workspace domain (such as `*.ws.copperflow.kurpeeren.com`) with either a wildcard certificate or on-demand certificates (the reverse proxy asks the hub's `/_tls-ask`).
7. **The workspace domain's site**: a separate domain for workspaces is recommended; with a subdomain of the same site the closed beta carries this limited risk: a hostile project page can stuff cookies that make the hub unusable in that browser until they are cleared (it cannot read or forge a session).
8. **The process runner**: until Task 3's container runner is in place, the hub runs only with `--trusted-accounts-only`, so every account can read every other account's data and the hub's keys; invite only people trusted with all of it.
